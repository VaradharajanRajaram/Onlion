Self-Billing Ordering System – High-Level Design
Meshyog will onboard food outlet owners by creating an Admin user in the system.
Admin user credentials will be shared with the food outlet owner.
The Admin user can create multiple food outlets. However, each outlet will be activated only after uploading a valid license obtained from Meshyog.
The Admin user can create new users with a Cashier role for their food outlets.
Cashier users can be assigned to any of the Admin’s food outlets.
User administration is completely managed by the food outlet owner (Admin user).
Both Admin and Cashier users are responsible for managing the menu, including:
Add
Remove
Update
Enable / Disable
The Admin user is able to:
Generate reports
View reports
Send reports
Download reports

---

🧠 How Super Admin is Created (Bootstrap Problem)

There are 3 standard approaches used in real systems:


---

✅ Approach 1: Default Super Admin (Recommended for your case)

You create a predefined Super Admin during application startup.

🔧 How it works

When your app runs for the first time:

System checks → “Is there any SUPER_ADMIN in DB?”

If NO, it creates one automatically




---

💻 Example (Spring Boot)

@Component
public class DataInitializer implements CommandLineRunner {

    @Autowired
    private UserRepository userRepository;

    @Autowired
    private PasswordEncoder passwordEncoder;

    @Override
    public void run(String... args) {
        if (userRepository.findByRole("SUPER_ADMIN").isEmpty()) {

            User superAdmin = new User();
            superAdmin.setUsername("superadmin");
            superAdmin.setPassword(passwordEncoder.encode("Super@123"));
            superAdmin.setRole("SUPER_ADMIN");

            userRepository.save(superAdmin);

            System.out.println("Super Admin Created");
        }
    }
}


---

🔐 Important

Store password encrypted (BCrypt)

Force password change on first login

Disable public registration for Admin



---

✅ Approach 2: Database Script (Production Preferred)

You insert Super Admin directly using SQL.

INSERT INTO users (username, password, role)
VALUES ('superadmin', '$2a$10$encryptedpassword', 'SUPER_ADMIN');

👉 Used in:

Production deployments

Controlled environments



---

✅ Approach 3: Environment-Based Creation (Advanced)

Use environment variables:


app.superadmin.username=admin
app.superadmin.password=securepassword

Create only if not exists


👉 Good for:

Cloud deployments

CI/CD pipelines



---

🏗️ Role Hierarchy Design

Define clear hierarchy:

SUPER_ADMIN
     ↓
ADMIN (Outlet Owner)
     ↓
CASHIER


---

🔐 Spring Security Role Setup

Example configuration:

@PreAuthorize("hasRole('SUPER_ADMIN')")
public void createAdminUser() {
    // only super admin can create admin
}

@PreAuthorize("hasAnyRole('ADMIN')")
public void createCashier() {
    // admin creates cashier
}


---

🔄 Full Flow (Recommended)

1. Application starts


2. System auto-creates SUPER_ADMIN (if not exists)


3. Super Admin logs in


4. Super Admin creates:

Admin (Outlet Owner)



5. Admin creates:

Cashiers

Outlets





---

⚠️ Common Mistakes (Avoid These)

❌ Allowing anyone to register as Admin
❌ Hardcoding password without encryption
❌ No role-based restriction
❌ Multiple Super Admins without control


---

🚀 Best Practice (For Your Project)

👉 Use Approach 1 (Auto Bootstrap) now
👉 Later upgrade to DB script / environment-based


---

💡 Pro Tip (Advanced Design)

Add a flag:

boolean isSystemGenerated;

So you can track:

Default super admin

Manually created users
